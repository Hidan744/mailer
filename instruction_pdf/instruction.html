Часть 1. Как пользоваться приложением

1.1. Вход

Откройте адрес приложения в браузере (https://<ваш-домен>), введите логин и пароль.

Создать дополнительного пользователя (например, ещё одному сотруднику) можно так — на сервере, в папке проекта:

docker compose exec app node dist/lib/createUserCli.js <логин> <пароль>

Той же командой с существующим логином можно сменить пароль (перезапишет старый). Удалить пользователя — через базу данных:

docker compose exec db psql -U mailer -d mailer -c "delete from \"User\" where username='<логин>';"
Все пользователи равноправны — ролей «администратор»/«только просмотр» в приложении нет, любой залогиненный может менять всё.

1.2. Настройки — сделать один раз перед первой кампанией

Раздел «Настройки» в верхнем меню.

Почтовый ящик (SMTP/IMAP)

Обязательно. Это ящик, от имени которого уходят письма и в котором ищутся ответы получателей.

  • «+ Добавить ящик» → заполнить SMTP/IMAP хост, порт, логин, пароль.
  • Важно: хост для подключения — это не всегда тот же адрес, что и домен почты. Если сертификат почтового сервера провайдера выписан на другое имя (частый случай у виртуального/shared-хостинга), нужно использовать именно то имя, на которое выписан сертификат — иначе будет ошибка ERR_TLS_CERT_ALTNAME_INVALID. Как узнать: dig -x <IP почтового сервера> покажет настоящий хостнейм сервера.
  • Кнопка «Изменить» у ящика — можно поправить любые поля позже, включая пароль (если оставить поле пароля пустым — прежний пароль сохранится).

Фирменный бланк

Логотип и подвал письма.

  • «+ Добавить бланк» → загрузить jpg с логотипом/реквизитами (верхний колонтитул), опционально — картинку для подвала и текст контактов внизу письма.

Нумерация исходящих писем

Под формат «Исх. № 0210/186».

  • «+ Добавить схему нумерации» → указать префикс (например «0210») и шаблон ({prefix}/{counter} — счётчик увеличивается на 1 с каждым отправленным письмом, можно настроить сброс раз в год).

1.3. Создание кампании

«Кампании» → «Новая кампания»:

  1. Название (для себя, получатели его не видят).
  2. Тема письма и текст (тело) — основной вариант. Шапка письма (исх. №, дата, должность/компания/ФИО получателя, обращение «Уважаемый...») добавляется автоматически — сюда вписывается только содержательная часть.
  3. Доп. варианты темы/текста (необязательно) — см. раздел 1.5 ниже про автоматическую ротацию текста.
  4. Почтовый ящик, фирменный бланк, схема нумерации — выбрать из настроенного в 1.2.
  5. Расписание: окно отправки (по умолчанию 9:00–17:00), обед (12:00–13:00 — в это время письма не уходят), интервал между письмами (по умолчанию 5 минут), часовой пояс (Asia/Yekaterinburg = время Перми).
  6. Порог ротации текста (50–100, по умолчанию 75) — см. 1.5.

1.4. Получатели и запуск

На странице кампании:

  1. «Импортировать из Excel» — выбрать файл, нажать саму кнопку импорта (это отдельный шаг от запуска рассылки!). Колонки файла: Компания, Должность, Фамилия И.О., Имя Отчество, Email (плюс любые дополнительные колонки — не используются, но не мешают). После импорта появится сообщение «Импортировано получателей: N», а счётчик «Получатели» увеличится.
  2. Только после этого — «Запустить рассылку». Письма уходят по одному, согласно расписанию кампании, полностью автоматически.
  3. Пока кампания идёт — статистика на странице обновляется при каждом обновлении страницы (браузер сам не обновляется, нужно нажимать F5 / перезаходить).
  4. «Приостановить» — остановить рассылку вручную в любой момент, «Запустить» снова — продолжить с того же места.
  5. Если несколько писем не ушли из-за временной ошибки (например, недоступен SMTP) — появится кнопка «Повторить ошибки (N)», она вернёт их в очередь.
  6. Кампания, у которой закончились получатели, переходит в статус done. Если нужно разослать ещё кому-то — импортируйте новый Excel в ту же кампанию и нажмите «Добавить получателей и продолжить» — уйдёт только новым, старые получатели повторно не потревожатся.
  7. «Скачать отчёт (xlsx)» — в любой момент, отчёт по отправкам/открытиям/ответам.

1.5. Ротация темы/текста каждые 50–100 писем

Есть два режима, оба соответствуют требованию не слать тысячи одинаковых писем подряд без разрыва:

  • Ручной (по умолчанию, если не заполнять доп. варианты). По достижении порога кампания сама встаёт на паузу со статусом «Требуется правка текста» — оператор заходит, правит тему/текст (или явно подтверждает «оставить как есть») и продолжает. Рассылка в это время не идёт, пока оператор не вмешается.
  • Автоматический. При создании кампании в блоке «Доп. варианты темы/текста» заполните от 1 до 4 дополнительных вариантов (тема + текст каждый). Тогда по достижении порога кампания сама переключается на следующий вариант по кругу и продолжает слать — без остановки и без участия оператора.

1.6. Отслеживание и отписка

  • Открытие письма — отслеживается через невидимый пиксель в письме. Метрика оценочная: многие почтовые клиенты по умолчанию блокируют показ картинок, пока получатель не разрешит явно — реальное число открытий может быть выше показанного.
  • Ответы — приложение раз в 5 минут проверяет входящие в подключённом ящике (IMAP) и сопоставляет ответы с отправленными письмами по технической метке в заголовках. Работает только если получатель отвечает через «Ответить» в своём почтовом клиенте (обычная практика) — если он пишет письмо заново на тот же адрес, оно не считается ответом на конкретное письмо кампании и просто останется в общих входящих.
  • Ссылка «Отписаться» — есть в каждом письме автоматически. Отписавшийся email больше никогда не получит писем ни из одной кампании этого приложения.

Часть 2. Полная передача заказчику

Сейчас приложение развёрнуто на сервере и почте исполнителя (VPS reg.ru 194.67.124.161, ящик rassylka@vinakovlab.online). Для полной передачи заказчику и его независимости — 152-ФЗ и просто чтобы исполнитель не был «точкой отказа» — нужно перенести всё на инфраструктуру заказчика.

2.1. Что должен приобрести/завести заказчик

  1. Свой VPS в России. Проверено на конфигурации 1 vCPU / 2 ГБ RAM / Ubuntu 22.04 — этого достаточно. Подойдёт reg.ru, Timeweb Cloud, Selectel, VK Cloud, Yandex Cloud и т.п. — приложение не привязано к конкретному хостеру.
  2. Свой домен (или поддомен на существующем домене заказчика) с доступом к управлению DNS-записями.
  3. Свой почтовый ящик на этом домене с доступом по SMTP и IMAP. Варианты: готовый сервис (Яндекс 360 для бизнеса, VK WorkMail) или почта на том же хостинге, где куплен домен (как сейчас у исполнителя на reg.ru). Для сервиса на shared-хостинге уточните у провайдера при подключении: 1) не блокирует ли он SMTP с внешних IP по умолчанию (у reg.ru блокирует, снимается обращением в поддержку), 2) правильный хостнейм для SMTP/IMAP-подключения (см. раздел 1.2 выше).

2.2. Что нужно сделать на новом сервере

Это можно сделать самому заказчику (если есть технический специалист) или исполнителю разово в рамках передачи — дальше сервер и все секреты полностью в руках заказчика.

  1. Получить доступ к коду: либо исполнитель передаёт права владения GitHub-репозиторием github.com/Hidan744/mailer заказчику (Settings → Danger Zone → Transfer ownership), либо просто передаёт архив с кодом без истории git.
  2. На новом сервере: 
    git clone <адрес репозитория>
cd mailer
sudo bash deploy/setup-server.sh
cp .env.example .env
  3. Заполнить .env своими, новыми значениями (не копировать значения исполнителя!):
    • POSTGRES_PASSWORD, CREDENTIALS_ENC_KEY, SESSION_SECRET — сгенерировать каждое отдельно: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
    • DOMAIN и PUBLIC_BASE_URL — домен заказчика (поддомен должен A-записью указывать на IP нового сервера)
    • ADMIN_USERNAME / ADMIN_PASSWORD — логин/пароль первого администратора заказчика
  4. Запустить: 
    docker compose up -d --build
  5. Открыть https://<домен заказчика> — Caddy сам получит бесплатный HTTPS-сертификат.
  6. Зайти под первым администратором, в Настройках подключить свой почтовый ящик (SMTP/IMAP), загрузить логотип/бланк, задать схему нумерации.
  7. Настроить у себя в DNS домена почты SPF/DKIM/DMARC для доставляемости (обычно провайдер почты создаёт их автоматически при подключении домена — как это было и у исполнителя на reg.ru).
  8. Провести тестовую отправку на 2-3 своих адреса перед боевым запуском.

2.3. Что не передаётся и почему

Сервер 194.67.124.161, ящик rassylka@vinakovlab.online и все текущие пароли/ключи шифрования (CREDENTIALS_ENC_KEY, SESSION_SECRET, пароль БД) — это инфраструктура и секреты исполнителя для тестового периода. Их не нужно и не следует передавать — заказчик заводит полностью свои, независимые ни от кого. После переноса сервер исполнителя можно отключить/удалить.

2.4. Перенос уже накопленных тестовых данных (опционально)

Обычно не требуется — боевая эксплуатация начинается «с чистого листа» на новом сервере. Если всё же нужно перенести тестовые кампании/получателей:

# на старом сервере — выгрузить базу
docker compose exec db pg_dump -U mailer mailer > backup.sql

# перенести файл backup.sql на новый сервер, затем там
docker compose exec -T db psql -U mailer mailer < backup.sql

2.5. Итоговый чек-лист передачи

  • Заказчик приобрёл VPS в РФ и домен
  • Заказчик завёл свой почтовый ящик с доступом SMTP/IMAP
  • Код передан (перенос прав на репозиторий или архив)
  • Приложение развёрнуто на новом сервере со своими секретами в .env
  • Домен указывает на новый сервер, HTTPS работает
  • Почтовый ящик подключён в Настройках, тестовое письмо реально доставлено
  • SPF/DKIM/DMARC настроены для домена почты
  • Логотип, бланк и схема нумерации заведены
  • Первый администратор может войти и всё это подтверждает лично
  • Сервер и почта исполнителя отключены/удалены
