# План запуска в боевую эксплуатацию

Зафиксировано по состоянию на 11.09.2026. Технически приложение готово (см. README) —
это план доведения до реальной боевой рассылки.

## Независимый аудит кода (11.09.2026)

Разобрали код построчно "как перед сдачей", нашли и починили 5 реальных багов (не
стилистика, а поведение, которое дало бы неверный результат на боевых данных):

1. Проверка отписавшихся была регистрозависимой (`Ivan@x.ru` ≠ `ivan@x.ru`) — отписавшийся
   мог получить письмо повторно, если email в новом списке набран с другим регистром.
2. Интервал между письмами считался только внутри одной кампании — две кампании на одном
   почтовом ящике, запущенные одновременно, реально удваивали скорость отправки с него,
   никак не предупреждая об этом.
3. Плейсхолдеры `{{Компания}}` и т.п. подставлялись в HTML-тело письма без экранирования
   спецсимволов — при определённых данных в Excel могло сломать вёрстку письма.
4. Удаление почтового ящика/бланка/схемы нумерации, которые уже используются кампанией,
   молча обнуляло связь в базе — кампания просто переставала слать без единого сообщения
   об ошибке. Теперь удаление блокируется с понятным текстом, что именно мешает.
5. На `/login` не было защиты от подбора пароля — добавлена блокировка на 15 минут после
   5 неудачных попыток с одного IP.

**Не баги, а риски на решение заказчика (не чинится кодом сейчас):**
- Один сервер, без автоматических бэкапов БД — при аварии сервера теряется вся база
  (кампании, получатели, история). См. этап 7.2.
- Нет глобального дневного лимита писем — только интервал между письмами и рабочее окно.
  Технически можно случайно запустить сразу несколько крупных кампаний одновременно.
- Таблица `AuditEvent` в схеме БД есть, но нигде не используется — то есть нет журнала
  "кто и что изменил" (все пользователи равноправны и безымянны в истории действий).
- Bounce-детект и сопоставление ответов — эвристика по заголовкам/отправителю, не 100%
  гарантия для всех форматов писем о недоставке у всех провайдеров.

## Доработка чек-пойнта ротации (п.5 ТЗ)

По умолчанию было: кампания сама останавливается каждые 50–100 писем и просит оператора
вручную поправить текст. По запросу заказчика добавили автоматический режим: при создании
кампании можно заранее заготовить 2–5 вариантов темы/текста — тогда по достижении порога
кампания сама переключается на следующий вариант по кругу, **без остановки рассылки**.
Если ни одного доп. варианта не заполнено — работает старое поведение (пауза на правку).

## Ручные исходящие номера

По запросу заказчика: если у конкретного получателя уже есть свой номер (например,
компания ведёт встречную переписку с уже присвоенным номером) — на странице кампании
можно раскрыть таблицу получателей и вручную вписать номер для нужных строк. Пустое поле —
как раньше, автонумерация по счётчику схемы. Заполненное — уходит именно этот номер,
счётчик схемы для такого письма не расходуется. Плюс добавили кнопку "Изменить" для
самих схем нумерации в Настройках (раньше можно было только удалить и создать заново).

## Дополнительные функции сверх ТЗ

По итогам анализа рынка добавили несколько улучшений:

- **Плейсхолдеры в тексте письма** — `{{Компания}}`, `{{Должность}}`, `{{ФИО}}`, `{{Имя}}`,
  `{{Email}}` теперь можно использовать в теме и теле письма (не только в автошапке),
  заменяются данными конкретного получателя при отправке.
- **Валидация email при импорте Excel** — строки с некорректным email или повторами внутри
  файла пропускаются с предупреждением, а не ломают весь импорт; повторный импорт не создаёт
  дублей получателей внутри той же кампании.
- **Детект отказов (bounce)** — IMAP-поллинг теперь распознаёт письма о недоставке
  (mailer-daemon/postmaster) и помечает такие письма отдельно от обычных ошибок отправки;
  видно в статистике кампании и в xlsx-отчёте.
- **Список отписавшихся** в Настройках — видно, кто отписался и когда, можно снять отписку
  вручную (этап 7.3 закрыт).
